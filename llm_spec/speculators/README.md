## 导言

本样例介绍基于 speculators 框架的草稿模型训练，当前覆盖 DSpark 草稿结构，后续其他草稿模型类型可在本目录下新增样例。本文以 DSpark 为例，将 DSpark 草稿模型技术扩展至 Qwen3.8-27B 与 GLM5.2 两个模型，并完成了完整的训练过程。在这两个模型上，我们训练出了可用的 draft 模型；DeepSeek 官方 DSpark 模型的接受长度在同一评测框架下一并列出，作为参考值。针对真实业务场景中暴露的问题逐一给出解决方案，场景覆盖 agent、中文、长序列、function call 与思考模式。全文共五章：第 1 章展示训练效果，第 2 章阐述训练思路与方案，第 3 章介绍消融实验结果，第 4 章介绍训练性能优化，第 5 章给出训练指导。

## 1. 训练效果

为了 DSpark 投机解码在 SOTA 大模型上真正可用，本文总结了一套DSpark模型训练方案，并基于这个方案为 GLM5.2 与 Qwen3.8-27B 训练出配套的 draft 模型，在真实业务场景（agent、中文、长序列、function call）中保持稳定的接受长度。围绕这个目标，全文依次讲四件事：场景问题的定位与解决（§2）、训练配方的消融确定（§3）、训练性能优化（§4）、沉淀出的方法论与训练指导（§5）。

实现的结果：两个SOTA模型上的草稿模型在真实业务场景（agent、中文、长序列、function call）取得稳定接受长度，DeepSeek 官方 DSpark 模型的接受长度在同一评测框架下作为参考值列出（§1.1）。三类接受长度退化逐一给出了数据可验证的解决方案（§2）。

本章展现最终训练效果两个模型的整体结果。评测口径：统一 draft checkpoint、num_speculative_tokens=8、bench 协议、开启思考模式、序列长度=1024。

### 1.1 草稿模型在各数据集上表现 AL

评测口径：AL（average accepted length，平均接受长度）含 bonus token，temperature = 0；表中 DeepSeek 官方列为另一 verifier（DeepSeek-v4-Flash）上测得的接受长度，在同一评测框架下作为参考值列出，两列不构成同条件对比。

|---|---|---|---|---|---|---|
| 数学 | GSM8K | 5.89 | 6.30 | 4.31 | +1.58 | +1.99 |

## 2. 训练思路与方案

我们的主要目的是探索SOTA模型在真实用户场景可用的草稿模型的训练方案，并训练出Qwen3.8-27B 与 GLM5.2 两个 SOTA 模型的可用DSpark模型。针对真实场景接受长度低的问题，我们将其分解为中文、长序列、function call三个子问题逐个击破（§2.2–§2.4），最终形成了在真实业务场景可用的草稿模型接受长度（§1.1）。

### 2.1 训练目标与问题定位

#### 2.1.1 背景：从论文复现到 SOTA 模型优化

在进入 SOTA 模型之前，我们先用 1.4M on-policy 再生样本训练 10 epoch 做了复现论证：humaneval / math-500 / gsm8k / mt-bench / alpaca / mbpp 六个评测集上的接受长度与论文内接受长度基本一致，验证了 DSpark 训练管线与框架的有效性。但在实际落地客户Agent场景时，发现这种方式训练出来的DSpark模型表现有明显退化，故针对SOTA模型我们进行了一系列针对性训练调整，最终实现与DeepSeek同等水平。

#### 2.1.2 问题与解决方案

| 类型 | 数据集 | 开源GLM5.2 DSpark模型A | 开源GLM5.2 DSpark模型B | DeepSeek DSpark模型 |
|---|---|---|---|---|
| Agent | 自研Agent | 1.5 | 1.15 | 3.97 |
| 中文 | Magpie | 2.34 | 2.38 | 3.02 |
| 长序列 | Longbench-v2 | 2.49 | 1.28 | 3.74 |
| ToolCall | BFCL-v3 | 3.25 | 2.66 | 3.82 |
| 通用对话 | Alpaca | 3.66 | 3.45 | 2.81 |

在 Agent 数据集上首测当时可用的 GLM5.2草稿模型时，我们发现即使在通用评测集上表现优秀的模型，在实际的Agent评测集上表现仍然不佳；而DeepSeek官方的DSpark草稿模型则是在通用对话领域表现不佳。针对自研Agent数据集上表现不佳的情况，我们观察了 Agent 数据集的样本特征，猜测退化集中在中文、长序列、function call三个维度；随后我们针对每个维度单独选取相应数据集评测，确认这三类数据上模型效果确实较弱，据此定位了出三个相互独立的问题。SOTA 模型（GLM5.2、Qwen3.8-27B）的训练即针对这三个问题逐个解决，调整后在 agent 数据集上的接受长度确实得到提升（§1.1），且最终发现模型在通用对话领域的数据集上接受长度同样达到较高水平（对照见 §1.1）。三个问题与对应解决方案总览：

| # | 问题 | 方案 | 详情 |
|---|---|---|---|
| 1 | 中文效果差：训练数据为英文再生数据，agent 场景中文占比高 | 中文数据加入预训练 | §2.2 |
| 2 | 长序列效果退化：agent 上下文超出 draft 训练长度，位置编码外推退化 | YaRN 长序列扩展 | §2.3 |
| 3 | function call：draft 未见过 function call token 分布 | 针对性增训 | §2.4 |

### 2.2 方案一：中文数据加入预训练

#### 2.2.1 解决方案

原始训练数据集仅包含英文数据，草稿模型上泛化能力不足。为提高中文 agent 场景下的接受长度，我们将中文数据混入英文预训练数据一同训练，期望模型在学到中文 agent 分布的同时保持英文能力不回退。中文数据由目标 verifier 自己重生成 assistant 回复（on-policy），英文部分同时用作不回退验证（§2.2.2）。

数据来源：

| 数据 | 来源 |
|---|---|
| 英文（原始训练数据） | [mlabonne/open-perfectblend](https://huggingface.co/datasets/mlabonne/open-perfectblend)（多子集合并数据集，各子集的原始比例有意义；两个样例的抽样口径不同：GLM5.2 侧对整池等概率随机抽 60w（见 glm5.2/README.md §6.2），Qwen3.8-27B 侧先按 source 分层抽 65w 再重生成、各子集比例精确保持（见 qwen3.8_27b/README.md §6.2.2）） |
| 中文 | [CMBTech/CMB-Eagle-Mix-330k](https://www.modelscope.cn/datasets/CMBTech/CMB-Eagle-Mix-330k)（ModelScope，Apache-2.0，33w 条中英混合，其中文部分即 swift/Chinese-Qwen3-235B-Thinking-2507-Distill-data-110k-SFT 蒸馏数据；两个样例同一个下载源、同一份选取脚本 `select_cmb_chinese_prompts.py`、同一口径）：按「中文占比 >= 0.24（分母=总字符数）」降序取前 10w，各自用本样例模型重生成——GLM5.2 侧 prepare 传两次加权到 20w（见 glm5.2/README.md §6.3），Qwen3.8-27B 侧复制加权到 15w（见 qwen3.8_27b/README.md §6.2.3） |

两类数据的 assistant 回复均由目标 verifier 自己再生（on-policy）后进入训练——draft 学的是 verifier 的分布，拿别的模型生成的回复当标签会引入分布偏移，中文数据不例外。

配比：GLM5.2 为中文 20w : 英文 60w，混入同一预训练数据集一起训，而不是单独训一个中文 draft。

#### 2.2.2 效果

对照：本次GLM5.2 DSpark模型（混中文训练）vs 开源GLM5.2DSpark模型（未训练中文数据），同一评测框架。

AL对照

| 数据集 | GLM5.2 DSpark（本次训练） | 开源GLM5.2 DSpark草稿模型A |
|---|---|---|
| GSM8K | 6.30 | 5.97 |
| MATH500 | 6.33 | 5.88 |
| HumanEval | 4.91 | 4.47 |
| MBPP | 4.58 | 4.16 |
| Magpie（中文数据集） | 3.65 | 2.4 |
| Alpaca | 3.87 | 3.66 |
| MTBench | 4.10 | 3.78 |
| LongBench-v2 | 4.48 | 2.49 |
| 自研Agent | 3.58 | 1.5 |

结论：

- 中文能力：混入中文后中文评测集 magpie AL = 3.65，远超开源权重。

- 英文不回退：混入中文后 gsm8k / humaneval / mbpp / math500 持平或更高——混入中文数据没有损伤英文能力。

### 2.3 方案二：长序列问题与 YaRN 扩展

#### 2.3.1 问题表现

开源GLM5.2的DSpark草稿模型（使用Default RoPe配置）在LongBench_v2数据集上的表现如下表所示：

| 长度桶 | 样本数 n | 平均接受长度（MAL） | 接受率（AR） |
|---|---|---|---|
| 0–32k | 30 | 3.65 | 32.0% |
| 32–64k | 30 | 3.16 | 26.0% |
| 64–100k | 30 | 2.34 | 16.1% |
| 100–140k | 30 | 2.22 | 14.1% |
| 140–172k | 26 | 1.97 | 11.6% |

观察：MAL 自 0–32k 桶的 3.65 起随长度单调下降，140–172k 桶 MAL 仅 1.97、AR 11.6%——大幅低于短桶（AR 32.0%）。结合训练序列长度 8192，退化随长度持续加深。AR 衰减比 MAL 更快（32.0% → 11.6% 约 −64%，3.65 → 1.97 约 −46%）说明问题不仅是平均接受 token 数下降，单 token 被拒比例也在恶化。

#### 2.3.2 解决方案：YaRN

问题本质：draft 的位置编码在训练时只见过 ≤ 8192 的位置分布，verifier 虽然原生支持长上下文（Qwen3.8 max_pos = 262k、GLM5.2 max_pos = 1M，均靠高 `rope_theta` 直接外推，没有配置 YaRN），但把 verifier 的 RoPE 配置原样复制进 draft 并不能让 draft 凭空学会在 100k+ 位置上工作——draft 的 MRoPE 维度从未在这些位置上收到过梯度。YaRN 是 draft 在训练短、推理长的设定下额外补做的一次外推配置。

本次训练采用方案：

| 位置 | 做法 |
|---|---|
| 训练端 draft RoPE | 由上游 `speculators.train` 从 verifier 拷贝基础的 `rope_parameters`，再加上 `rope_theta`。这条拷贝仅对齐 verifier 原生配置，不携带任何外推策略；使用default的rope配置搭配短序列预训练后，将配置改为yarn，再搭配长序列进行一轮增训可以获得效果最佳性价比最优的效果 |
| 训练序列长度 | 保持 8192，覆盖插值后的短程区间；低频维不插值，长程外推由 YaRN 的 NTK 段承担；预训练后可混入32k长度长序列搭配yarn配置进行增训，提高模型在yarn配置下的表现能力 |
| 推理端 | draft 的 rope_parameters 改为YaRN，verifier 侧 --max-model-len 决定实际档位；draft 的 factor  必须与该档位的扩展倍数匹配。 |

GLM5.2 的 DSpark模型RoPE 配置：

| 字段 | 值 |
|---|---|
| rope_theta | 8,000,000 |
| rope_type | YaRN |
| max_position_embeddings | 1,048,576 |
| factor | 32（外推倍率） |

GLM5.2主模型的长序列能力不是靠 RoPE 缩放获得——verifier 原生支持 1M 上下文，draft 则通过YaRN外推获得同等上下文效果。

#### 2.3.3 最终效果

本文训练的GLM5.2 长度桶结果（default AL vs yarn AL）：

| 桶 | default AL | yarn AL |
|---|---|---|
| 0–32k | 4.38 | 4.49 |
| 32–64k | 4.32 | 4.54 |
| 64–100k | 3.74 | 4.19 |
| 100–140k | 3.55 | 3.87 |
| 140–172k | 3.88 | 4.33 |

观察：

- default 配置下接受长度随长度增长下跌：AL 从 0–32k 桶的 4.38 一路降到 100–140k 桶的 3.55（−0.83，约 −19%）；140–172k 桶的回升（3.88）属桶间样本构成差异，长桶整体显著低于短桶的衰减形态不变。

- 改为 yarn 后全面回升：5 个桶全部回升（+0.11 ~ +0.45），整条曲线抬高且更平——64–100k 与 140–172k 各 +0.45（约 +12%），收益集中在 64k 以上，与 §2.3.1 的退化区间（80k 后 MAL 明显回落）对应：YaRN 补上的正是 draft 训练时没见过的长程位置。

- 与 Qwen3.8 对照（§2.5.3）：GLM5.2 draft 在 default 下退化更缓和（最低桶 3.55 vs Qwen3.8 的 2.37），yarn 增益幅度相应更小（长桶 +0.32~+0.45 vs +0.77~+2.21），但方向一致——长桶增益显著大于短桶。

#### 2.3.4 配置要求与注意事项

核心要求：不能从 0 带 yarn 训短序列，会直接导致长序列崩盘。YaRN配置可使用方案含以下两种：①短序列搭配default配置预训练，推理时直接修改配置文件为YaRN配置，成本最低；②短序列搭配default配置预训练后混合长序列搭配YaRN配置增训一轮，效果最佳；具体数据可见§3.1的消融实验。

### 2.4 方案三：Function call 数据增训

背景：Function Call 是 agent 场景中接受长度退化的独立因素之一（§2.1.2）：基线草稿模型的训练数据不含函数调用形态，drafter 未见过 tool_call 的 token 分布。

实验目标：通过针对性增训提升 tool_call 能力（以 agent_toolcall_eval 接受长度衡量），同时将通用能力退化控制在噪声带内。

#### 2.4.1 问题表现

在中文（§2.2）与长序列（§2.3）能力都已超过 DeepSeek 官方 DSpark 的情况下，自研 agent 数据集上的接受长度仍弱于 DeepSeek。归因：自研 agent 数据集带 function call 形态，drafter 的训练数据从未见过这类 token 分布。

|   | 数据集 | Qwen3.8-27B DSpark | GLM5.2 W4A8C8 DSpark | DeepSeek 官方 | Δ（Qwen3.8−DS） | Δ（GLM5.2−DS） |
|---|---|---|---|---|---|---|
| 通用中文 | Magpie | 3.35 | 3.65 | 3.02 | +0.33 | +0.63 |
| 长序列 | Longbench-v2 | 4.29 | 4.48 | 3.74 | +0.55 | +0.74 |
| Agent | 自研Agent数据集 | 3.7 | 3.58 | 3.97 | -0.27 | -0.39 |

先验证了公开 FC 数据集增训能否补上这个缺口——不能。在 dsv4-agent / glm52-agent / toolcall_en / bfcl_en 四个 FC 评测集上各做单数据集增训（1 epoch），收益只落在训练集自己的评测上，其余评测集普遍下降：仅 dsv4-agent数据集 增训后 dsv4-agent数据集 3.48 → 4.39，但 glm52-agent 2.79 → 2.35、toolcall_en 3.24 → 2.86、bfcl_en 3.52 → 3.16；仅 glm52 增训后 glm52 涨到 3.47，其余三集全部下降。唯一的相互迁移发生在结构类似的一对上——toolcall_en 与 bfcl_en 同为英文短上下文开放 API 形态，仅 toolcall 增训后 bfcl_en 3.52 → 3.86，仅 bfcl 增训后 toolcall_en 3.24 → 3.32。结论：FC 增训没有泛化能力，只有 function 结构内容类似的数据集之间有泛化；要提升哪个分布，就得用哪个分布的数据。

#### 2.4.2 解决方案

整体思路：把自研 agent 数据集里带 function call 的数据挑出来，混合原始（预训练）数据增训。§2.4.1 已证明跨数据集泛化走不通，故直接使用该自研数据集进行增训，训练数据直接对齐生产环境的分布，混入的原始数据起到防止通用能力回退的作用。

自研 agent 数据集处理过程：

| 编号 | 步骤 | 目的 | 关键操作 / 说明 |
|---|---|---|---|
| 1 | 样本分析 | 为后续整体的数据处理提供依据 | 全量统计会话数、对话轮数、token 长度分布、语言构成、工具调用类型、工具 schema 覆盖率、末轮角色分布 |
| 2 | 数据清洗 | 排查噪声信号提升训练样本质量 | 去除不触发工具调用的问候类样本；剔除无 tools 定义样本；同一会话仅保留最后一轮，避免重生成后样本重复；(以上处理依样本分析结论判断适用性，不同场景不一定适用） |
| 3 | 格式对齐 | 确保原始样本可被重生成脚本直接处理 | 统一字段与角色命名；补齐调用标识；修正工具调用与返回的配对关系 |
| 4 | 长样本裁剪 | 满足模型最长序列长度约束 | 长样本通常轮次较多，依据训练模型上下文长度对部分对话执行头部裁剪，丢弃最前面的历史对话，保留系统提示与临近的上下文； |
| 5 | 数据标记 | 生成评测集并防止数据泄露 | 预留 200 个样本作为评测集并登记会话级排除清单，训练样本生成时予以排除，确保训练集与评测集零重叠 |
| 6 | 数据重生成 | 去除重生成后的低质量样本 | 以目标模型（verifier）重新生成回复替代原始标签；长度截断（输出超上限）→ 整条丢弃；多工具截断（单次生成含多个调用，无法与下文返回一一对应）→ 脚本自然截断，可保留，不影响质量 |
| 7 | logits 对齐验证 | 确认该类样本训练收益可迁移至线上推理 | 对同一样本分别计算训练侧与推理侧前向 logits 并逐位比对； |

学习率与配比：沿用配方实验定型的两条原则——① 学习率 1e-5（1e-5 档通用集与基线持平、目标集仍有约 +10% 提升）；② replay 数据按通用评测题型对齐选取，与目标数据有效 token 比例 约 1 : 1。本次增训使用了1w条自研Agent数据集内function call数据混合1k条原始预训练数据增训，共增训3个epoch。

### 2.6 训练方法论

在 Qwen3.8-27B / GLM5.2 的草稿模型训练过程中，我们把流程沉淀为可复用的四步：对齐先行 → 数据构建 → 训练配方 → 评测驱动迭代。接入任何新 verifier 都按这四步走。

#### 2.6.1 第一步：对齐先行（logits 对齐验证）

每个新框架（verifier）接入后，第一件事不是训练，而是验证「训练优化的目标」与「推理时的行为」逐元素一致：

1. 训练侧重建的 verifier targets 与 verifier 真实前向数值对齐：用真实 checkpoint 权重过一遍 targets 重建链路，比对 rel-L2 / KL / top-1 概率。norm 类错配（gain 约定按家族选错）只有这个手段能暴露——训练照常收敛、无任何报警，数值比对才显示 rel-L2 高达 0.51。

2. 训练↔推理的五条不变量逐项核对（RoPE 位置、KV 边界、slot 目标、markov prev_token、norm 类）。同一架构族内做一次即可；换 verifier 家族时重核对家族相关项（如末层 norm 类）。

对齐不过关就开训，结局是「训练指标正常、vLLM bench accept_length 崩（~1.0–1.1）」。

#### 2.6.2 第二步：数据构建（on-policy 再生 + 配比挑选）

- on-policy 再生是底线：draft 学的是 verifier 的分布，所有训练数据（预训练与增训）的 assistant 回复一律由目标 verifier 自己重生成；regenerate / train / bench 三处模型 + chat template 必须一致。

- 配比按场景缺口挑选，用不回退验证兜底：

| 场景缺口 | 配比做法 | 验证口径 |
|---|---|---|
| 中文 | 中文与英文按 §2.2.1 配比混入预训练 | 英文评测集不回退（§2.2，Qwen3.8 对照见 §2.5.1） |
| Function call | 自研 FC 数据 + 原始数据增训，replay 题型对齐、总 token ≈ 1 : 1 | 通用评测集持平（§2.4，Qwen3.8 对照见 §2.5.2） |
| 长序列（YaRN） | 换 yarn 后长 + 短序列混合增训 1 epoch（§3.1 路径②） | 短序列回到 default 水平（§3.1） |
| 思考模式 | think 数据由 verifier 重生成 | 通用能力不回退（§2.5） |

- 两条配比原则（FC 配方实验定型，§2.4.2）：增训学习率 1e-5；replay 按通用评测题型对齐选取，控制变量看总 token 而非样本数。

- 不指望跨分布泛化：单数据集增训只涨自己（§2.5.2），要提升哪个分布就用哪个分布的数据，靠 replay 保证其余分布不掉。

#### 2.6.3 第三步：训练配方（数据量与超参）

| 阶段 | 数据量 | 轮数 | 学习率 |
|---|---|---|---|
| GLM5.2 思考模式 预训练 | 80w on-policy | 5 epoch | 3e-4 |
| Qwen3.8-27B 思考模式 预训练 | 80w on-policy | 5 epoch | 6e-4 |
| 场景增训（FC，§2.4） | 目标1-3w + 原始数据1-3w | 3 epoch | 1e-5 |

结构超参全系列一致：block_size=8、draft 5 层、markov rank 256、loss {"ce":0.1,"tv":0.9}、AdamW；取层按 §3.2 消融结论全深度均匀取 5 层进 fc，末层是否进 fc 按模型定：GLM5.2 取层含末层（5 23 42 60 78），Qwen3.8-27B 取 1 16 31 46 61（不含末层，末层仅作 tv-loss 标签源，对应 §3.2.4 的组1 形态）。我们在多次测试中发现1~2B左右的DSpark模型在openperfectblend数据集上，训练长度在8192时基本在25w-30w步左右会趋于收敛，故最终选择了80w数据预训练5轮，预训练时的学习率可以选择3e-4或6e-4，增训时学习率设置1e-5不会造成原始能力退化。

#### 2.6.4 第四步：评测驱动的迭代

固定三口径评测定位问题：常规 AL（通用能力）、agent AL（业务场景）、长序列数据集 AL\中文数据集AL\FunctionCall数据集AL（单点问题）。发现缺口 → 归因到数据分布 → 用对应数据增训（第二步）→ 三口径不回退验证后交付。第 2 章的三个方案（中文 / 长序列 / FC）都是这个循环的实例；结构类配方（取层、YaRN 路径、量化档位）在循环之外由消融实验（§3）单独确定。

## 3. 消融实验

本章单独收录确定训练配方的三组消融：YaRN 训练路径（§3.1）、hidden-state 取层策略（§3.2）、训练用 verifier 的量化档位（§3.3）。

### 3.1 长序列YaRN配置方法消融实验

#### 3.1.1 实验设计：三条候选路径

- 直接换 yarn 短序列全掉点：YaRN 的分段插值作用于全位置区间的编码（不只是长程），短序列上 draft 见到的波长整体重排——平均长度 ~1k 的 7 个数据集 AL 下降 0.06–0.30。

| 24–32k | 11 | 2.48 | 1.3–1.9 × 4，2.3–3.5 × 7 |
| 32–48k | 15 | 2.58 | 双峰：1.0–1.3 × 6，2.4–5.2 × 9 |

对比路径① 的 yarn 结果（0–32k 桶 AL 4.24）：从 0 带 yarn 训出的 draft 从 8k 起就接近全拒（多数样本 AL 1.1–1.4），32–48k 桶呈双峰分布——一半样本 1.0–1.3 完全失效，另一半 2.4–5.2。短序列训练给不了 yarn 插值后长程位置任何监督信号，从 0 起训还会把插值编码过拟合到短位置区间；路径② 增训轮的长序列数据正是用来补上这部分位置的。

#### 3.1.5 实验结论
结论：可行路径有两种分别是成本最低和效果最优，①default + 短序列配置预训练，推理直接改yarn配置，成本最低； ②default 配置预训练，改 yarn 后用长 + 短混合数据增训一轮，效果最优；③ 从 0 带 yarn 训短序列不可行。

### 3.2 Hidden-state 取层消融

#### 3.2.1 实验矩阵（载体：Qwen3-30B-A3B，48 层）

五组实验的唯一变量为取层位置：数据、词表、超参、训练步数完全一致。所有组的取层均含末层输出（id 48）作为 tv-loss 标签源，差别仅在于进入 fc 的特征层。

| 组 | 目录 | 进 fc 的特征层 | 取层方式 | AL | AR |
|---|---|---|---|---|---|
| 组1 | baseline_even5 | 1 12 23 34 45 | 均匀 5 层，不含末层 | 4.354 | 0.635 |
| 组2 | even5_last | 4 15 26 37 48 | 均匀 5 层，含末层 | 4.372 | 0.638 |
| 组3 | last5 | 44 45 46 47 48 | 非均匀：末 5 层密集 | 4.266 | 0.624 |
| 组4 | last3 | 46 47 48 | 非均匀：末 3 层密集 | 4.184 | 0.615 |
| 组5 | last1 | 48 | 非均匀：仅末层 | 3.980 | 0.595 |

AL 为接受长度（accept length），AR 为接受率（accept rate），均取训练结束时的验证值。

排序（AL 由高到低）：组2 > 组1 > 组3 > 组4 > 组5

#### 3.2.2 结论

取层方式：在全部深度上均匀取层，并包含最后一层。

1. 层数需充分。 在同样末端集中的条件下，3 层 → 5 层（组4 → 组3）AL +0.082。

2. 分布需均匀。 同为 5 层、fc 输入维同为 10240，由末端集中改为全深度均匀（组3 → 组2）AL +0.106。

3. 末层需进入 fc。 组2 与组1 同为 5 层全深度均匀取层、fc 输入维同为 10240，差别在于均匀取层的端点是否落在末层（组1 止于 id 45、末层仅作为标签源；组2 含 id 48）。组2 高 +0.019——末层本身即 targets 的来源，兼作 fc 的一路输入可带来小幅正收益。该组对中 4 个中间层的位置亦整体上移，故此收益幅度仅供参考。

#### 3.2.3 实验载体

五组实验均在 Qwen3-30B-A3B 上完成（48 层，hidden_size 2048，fc 输入维随取层数为 2048 / 6144 / 10240）。

#### 3.2.4 适用范围

结论适用于实际取层结构相同的配置，即同时满足：

- 相同的 id 语义（id k = 第 k 层输出，末层落在 id L）

- 末层作为 targets / tv-loss 的标签源

- 全部取层项进入 fc

满足上述前提时，结论可从 Qwen3-30B-A3B 外推至其它总层数的模型（含现役 GLM-5.2 的 5 23 42 60 78）。

与 Qwen3.8-27B 实际取层的对照：Qwen3.8-27B（64 层）实际 --target-layer-ids 为 1 16 31 46 61，按 §3.2.1 的取层分类对应「均匀 5 层，不含末层进 fc」（末层 id=64 仅作 tv-loss 标签源），结构等价于组1（1 12 23 34 45 在 48 层下），与本节「全深度均匀 + 含末层」最优组2 的差距按结论 3 量级约为 +0.019 AL。

### 3.3 训练量化档位：w4a8 训练 + w8a8 部署

结论：训练侧用 w4a8 量化的 GLM5.2 作 verifier，产出的 draft 部署时搭配 w8a8 主模型，接受长度不下降，可用；训练算力成本约节省50%。

依据：训练链路的算力大头是 verifier 前向——数据重生成、hidden-state 抽取、tv-loss 标签重建都要跑 verifier，w4a8 的前向开销显著低于 w8a8。draft 学的是 hidden state → logits 的映射，w4a8 与 w8a8 verifier 之间的差异不影响 draft 质量（接受长度不掉）。

同一份 w4a8 训练的 draft，分别部署在 W4A8C8 与 W8A8 两种 GLM-5.2 主模型上的接受长度：

| 数据集 | W4A8C8 部署 AL | W8A8 部署 AL |
|---|---|---|
| GSM8K | 6.30 | 6.41 |
| HumanEval | 4.91 | 4.97 |
| MATH500 | 6.33 | 6.33 |
| Magpie | 3.65 | 3.61 |
| MBPP | 4.58 | 4.70 |
| Alpaca | 3.87 | 3.93 |
| MTBench | 4.10 | 4.16 |

训练成本：提取hidden-state：2×A3， 训练：1×A2。相比 W8A8 全程训练，w4a8 训练节省约一半算力。

## 4. 训练性能优化

训练全链路里最容易被低估的瓶颈不是训练前向/反向本身，而是 verifier 侧 hidden-state 的供给速率：vLLM 抽取 HS → 落盘 → 训练 connector 读取 → dataloader 取样本——任一环节供给跟不上，NPU 就在等数据。本章从Hidden States服务提取吞吐、异步落盘、跨机传输效率等方面对训练性能进行了优化，GLM5.2及Qwen3.8优化前后性能对比如下表：

| 模型 | 优化前步速 | 优化后步速 | 优化前单卡训练吞吐 | 优化后单卡训练吞吐 |
|---|---|---|---|---|
| GLM5.2 | 5.5s/步 | 2.91s/步 | 1430 tok/s | 2700 tok/s |
| Qwen3.8-27B | 1.69s/步 | 1.37s/步 | 4817 tok/s | 5960 tok/s |

优化项总览如下：

| 优化项 | 提升效果 |
|---|---|
| 多 endpoint 并行（§4.1） | 训练从「数据饥饿」变为「算力瓶颈」：fetch 等待只占 step ~5%，NPU 满负荷 |
| safetensors ≥ 0.8.0 + worker 调优（§4.2） | step 1100ms → 571ms（+48%），供给余量 −40% → +18%，fetch 尖峰消除 |
| HTTP 传输后端（§4.3） | file → http：step 均值 605.9 → 576.9ms（约 −29ms/step）、fetch 延迟 91.1 → 54.3ms；官方 mooncake 后端与 http 吞吐相当 |

### 4.1 多 endpoint 并行：每rank一或多vLLM 服务

每个 training rank 配一个或多个独占的 HS 生成 vLLM endpoint（4 卡训练 → 4 个 endpoint，2 台专用机 × TP=2，共 8 张专用卡，不占训练节点算力），目的是让vllm推理服务侧生成HS的吞吐速度能超过训练消耗吞吐速度，以下为Qwen3.8-27B训练数据：

| endpoint 数 | 4 个 rank 的 hidden-state 供给 | 训练状态 |
|---|---|---|
| 2 个（4 rank 共享） | 2 个 TP2 vLLM 的 prefill 吞吐 < 4 rank 消耗 → prefetch buffer 抽干 | 数据饥饿：fetch_ms 暴涨 → 慢 |
| 4个 （一个rank一个endpoint） | 仍不足以同时喂饱 4 rank | 部分数据饥饿 → 偏慢；约1.82s |
| 8个（一 rank 两个endpoint） | 每个 endpoint 供 1 rank，总吞吐 ≈ 消耗 | 算力瓶颈：NPU 几乎满算，瓶颈在训练前向/反向本身 → 最快；约1.37s |

### 4.2 safetensors 升级与 worker 调优

早期在线训练 step 慢的根因是 vLLM connector 写 hidden states 文件时 safetensors < 0.8.0 持 GIL——example_hidden_states_connector.py 用 ThreadPoolExecutor(num_writer_threads=8) 写 hs，但 safetensors 0.7.0 的 save_file() 持 GIL 导致 8 线程实际串行，arrival 远小于训练消费速度，prefetch 池周期性耗尽导致 fetch 间歇尖峰。

升级 safetensors 到 0.8.0（`pip install safetensors>=0.8.0 --no-deps`）。以下数据来自 Qwen3-30B-A3B 训练：

| 配置 | step_ms | arrival | 余量 |
|---|---|---|---|
| 0.7.0 + 16w pref4 | 1100 | 10.8/s | −40% |
| 0.8.0 + 16w pref4 | 739 | 16.3/s | −9% |
| 0.7.0 + 24w pref4 | 962 | 11.9/s | −34% |
| 0.8.0 + 24w pref4 | 571 | 20.7/s | +18% |

step 1100ms → 571ms（提升 48%），供给余量转正，fetch 尖峰基本消除。

### 4.3 新增传输后端（HTTP方案 vs MoonCake方案）

使用file backend将HS文件落共享盘以实现跨机训练时， vLLM 把每个样本的 hidden state（503MB–2GB）写到 cephfs 共享盘，瓶颈集中在写路径。为解决该时延导致的训练性能问题，我们将HS 落盘从共享盘（cephfs）改为各 endpoint 本地盘，并开发功能使训练端通过 HTTP 拉取（--hidden-states-backend http，endpoint_train.py 注入各 endpoint 的 HS 服务地址）。该功能开发期间，上游官方基于 mooncake 的传输方案尚未完全成熟，因此先行自研 http 后端；目前上游 mooncake 后端已可直接使用。为此我们又对两套后端进行了在线对照实验（live A/B），结果表明二者性能相当，吞吐无显著差异。

file（共享盘）vs http（实验模型：Qwen3-30B-A3B）：

| 配置 | step_ms 均值 | get_generated_ms 均值 | fetch_ms 均值 |
|---|---|---|---|
| file backend（20ms poll） | 605.9 | 368.1（wait_lock_ms） | 91.1 |
| http backend | 576.9 | 359.6（http_get_ms） | 54.3 |

http 较 file 快 ~29ms/step，收益主要来自MDS 饱和突发延迟。

mooncake vs http（实验模型：Qwen3.8-27B，在线对照实验；两组配置逐行对齐——同 8 端点、同 seed（shuffle 一致），按 step 序号对齐同批数据，唯一变量为传输后端）。

实验一：8k 短样本，HS数据生成速度不造成瓶颈（step_ms，单位 s）：

| step窗口 | 后端 | n | mean | p50 | p90 | p99 | max |
|---|---|---|---|---|---|---|---|
| 50-500 | http | 451 | 1.37 | 1.34 | 1.54 | 1.74 | 1.8 |
| 50-500 | mooncake | 451 | 1.36 | 1.34 | 1.51 | 1.67 | 1.72 |
| 500-1550 | http | 1051 | 1.37 | 1.36 | 1.55 | 1.72 | 2.2 |
| 500-1550 | mooncake | 1051 | 1.36 | 1.35 | 1.51 | 1.68 | 2.21 |

实验二：32k 长样本，瓶颈主要在HS生成速度，差异可能来源于HS生成速度波动。两组训练在同一 step 区间（29185–29476，n=291；shuffle 一致，逐步同批对齐）比较 step_ms（单位 s）：

| 后端 | n | mean | p50 | p90 | p99 | max |
|---|---|---|---|---|---|---|
| http | 291 | 5.37 | 2.41 | 16.21 | 42.96 | 46.0 |
| mooncake | 291 | 5.75 | 2.25 | 18.89 | 50.30 | 55.4 |

结论：在两种训练形态（compute-bound 的 8k 与 generation-bound 的 32k）下，传输均不在关键路径上，mooncake 与 http 吞吐相当（均值差异 ≤1%）。mooncake 的收益并非体现在吞吐，而在于：尾部无 flock/cephfs 毛刺（warmup 后 max 2.2s，http 长跑偶发 36–68s 尖刺）、HS 不落 cephfs（节省每样本 503MB–2GB 的瞬时双写，无孤儿文件堆积）、逐样本传输时延/带宽可观测（22,597 个样本取数 p50 271ms / p99 5.5s，0 超时 0 失败），以及后续 tcp→RoCE 的演进空间。

上述三项优化中，仅 HTTP 传输后端涉及上游代码改动（PR [#1011](https://github.com/vllm-project/speculators/pull/1011)），由于上游采用mooncake方案故未合入主干，http 后端亦不随本仓库样例发布。**后续建议直接使用官方 mooncake 方案**——本仓库样例即基于官方 mooncake backend 组织。
